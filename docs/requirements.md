# 要件定義

## 1. 目的とスコープ

SQL本文をGitHubリポジトリに保存せず、AWS上のWeb UIでSQLパッチを申請・検証・承認・実行・監査する。個人開発ではダミーデータと検証用PostgreSQLだけを使用し、社内導入時に認証、ネットワーク、DB接続先、承認ルールを差し替えられる設計にする。

本Phaseで確定するのは、初回リリースに必要な機能を含む詳細設計、脅威と安全対策、状態遷移、データモデル、API、UI、運用、構成図、実装計画である。AWSリソースの作成、CDK実装、デプロイ、実DB接続、SQL実行は対象外とする。

## 2. 利用者と責務

| 利用者 | 責務 |
| --- | --- |
| アップロード者 | パッチ作成、ファイルアップロード、ドライラン、承認申請、必要時のロールバック申請、自己申請の履歴確認 |
| 指定承認者 | 担当環境・担当申請の内容とログを確認し、本実行またはロールバックを承認・却下 |
| 運用管理者 | ユーザー・承認者・環境設定・保持期間を管理。通常のSQL本文閲覧権限は持たせず、緊急アクセスは別ロールで監査 |
| システム | S3整合性検証、状態遷移、非同期起動、重複防止、ログ保存、監査記録、異常時の手動確認待ちへの遷移 |

## 3. 必須機能要件

| ID | 要件 | 受入条件 |
| --- | --- | --- |
| FR-01 | Cognitoログイン | 未認証の画面・API・S3への直接アクセスが拒否される。S3署名付きURLは、APIで認可した利用者へ短時間だけ発行するBearerアクセスとして監査・制限する |
| FR-02 | フォルダアップロード | `dry-run.sql` と `execute.sql` 必須、`rollback.sql` 任意。ファイル名、拡張子、サイズ、個数、構成をサーバー側で検証する |
| FR-03 | 改ざん検知 | S3 VersionIdとSHA-256をFile項目に記録し、完了後の差し替えを拒否する |
| FR-04 | リビジョン | SQL修正は新しいRevisionとし、ドライラン・承認をリセットする。承認済みRevisionのS3キーを再利用しない |
| FR-05 | ドライラン | `dry-run.sql` を実行し、変更系SQL、件数、SELECT結果、エラー、実行時間、ROLLBACK確認結果を履歴保存する |
| FR-06 | ドライランゲート | 成功、タイムアウト、状態不明、ROLLBACK未確認を区別し、成功以外は承認申請できない |
| FR-07 | 承認 | 指定承認者だけが承認・却下でき、申請者本人は承認できない |
| FR-08 | 本実行 | 承認後に追加操作なしで非同期実行し、承認済みVersionId・SHA-256を実行直前に再検証する |
| FR-09 | 重複防止 | 同一操作の二重申請・二重CodeBuild起動・二重SQL実行を条件付き更新と実行ガードで防止する |
| FR-10 | 状態不明 | CodeBuildまたはDBのACKが不明な場合は自動再実行せず、`UNKNOWN` として手動確認を要求する |
| FR-11 | ロールバック | 任意の `rollback.sql` について申請・別担当者承認・自動実行・履歴保存を行う |
| FR-12 | ログ閲覧 | S3の暗号化済みログをターミナル形式の安全なテキストとして表示し、権限のある利用者だけが短期URLで取得する |
| FR-13 | 監査 | 閲覧、ダウンロード、申請、承認、却下、実行、設定・権限変更、緊急アクセスを不変履歴として記録する |
| FR-14 | 環境分離 | 開発・検証・本番ごとにCodeBuild、IAM、Secret、Security Group、DB接続先、承認権限を分離する |
| FR-15 | 復旧 | RDSバックアップ、PITR、手動復旧をロールバックSQLとは別の復旧手段として定義する |

## 4. SQLファイル制約（初期値）

初期値は設定で変更可能だが、変更は管理操作として監査する。個人開発では10 MiB/ファイル、30 MiB/Revision、3ファイルまでを推奨する。社内導入時はDBロック時間、実行時間、業務影響で再評価する。

- 許可ファイル名は `dry-run.sql`、`execute.sql`、`rollback.sql` のみ。
- パス区切り、隠しファイル、追加のSQL・シェル・バイナリを拒否する。
- UTF-8を基本とし、サイズ上限、合計サイズ、Content-Length、S3チェックサムを検査する。
- 指定されたS3 prefix外のキー、想定VersionId以外、アップロード完了前のオブジェクトは実行対象にしない。
- SQL本文は画面の一覧・DynamoDB・通常のCloudWatchアプリログには出さない。

## 5. 非機能要件

| 分類 | 要件 |
| --- | --- |
| 機密性 | S3 Block Public Access、TLS強制、S3 Versioning、暗号化、最小権限IAM、短期署名URL |
| 完全性 | S3 VersionId・SHA-256・ETagを混同せず扱い、実行直前にVersionIdとSHA-256を再検証。ETagは補助メタデータであり完全性の根拠にしない |
| 可用性 | Web/APIの一時失敗は再試行可能にするが、SQL実行の状態不明を自動再実行しない |
| 監査性 | 操作者、承認者、対象Revision、環境、実行ID、CodeBuild ID、時刻、結果S3キーを追跡可能にする |
| 性能 | リアルタイムログ配信は不要。ログは完了後にページングまたは表示上限付きで取得する |
| コスト | NAT Gatewayを標準採用せず、実行環境の依存物を固定イメージへ焼き込む。容量、ログ、CodeBuild時間、KMS、VPC Endpointを監視する |
| 保守性 | CDKコンテキストまたは環境設定で接続先・承認ルール・上限・保持期間を変更できる |

## 6. 制約と明示する限界

- PostgreSQLトランザクションで通常のDML・一部DDLを巻き戻せても、シーケンス、外部システム、トリガーが呼ぶ外部処理、拡張機能、FDWなどすべての副作用は保証できない。
- `dry-run.sql` と `execute.sql` が別ファイルである以上、ドライランの成功は本実行SQLの安全性を証明しない。両ファイルのSHA-256と差分をUIに表示し、承認者の確認責任を残す。
- ロールバックSQLは元の状態を必ず復元するものではない。バックアップ・PITR・手動復旧を優先順位付きで運用する。
- AWS管理者やアカウントルート相当の特権を完全に見えなくする設計ではない。アプリの通常権限とAWS特権アクセスを分離し、CloudTrail・緊急アクセス監査を行う。

## 7. Open Questions

1. 社内導入時のIdPはCognito単独か、SAML/OIDCフェデレーションか。
2. 本番の承認者を申請ごとに指定するか、環境・サービス所有者グループから自動割当するか。
3. 本番で許可するDDL、許容ロック時間、最大実行時間、DBの同時実行数。
4. SQL・ログの法定保持期間、削除承認、法的ホールドの要否。
5. 社内導入時にTools/Dev/Test/ProdのAWSアカウントを分離するか。
6. RDS認証をSecrets Manager管理パスワードからIAM DB Authenticationへ移行するか。
7. 対象DBへ `sql_patch_manager.execution_ledger` を事前プロビジョニングできるか。保持期間、DBA所有者、dry-run時の台帳書込みをどう扱うか。
